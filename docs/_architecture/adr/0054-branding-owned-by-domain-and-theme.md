# ADR-0054: Branding owned by the domain, palettes and derivation by the theme, colours that resolve with their palette

## Context and Problem Statement

`FR-14` and `FR-53` ask for an application name, motto, logo and colours that an admin sets globally and a quiz can override. Open were where the texts, the logo and the custom colours are stored, whether they are catalogue settings ([ADR-0042](0042-settings-inherited-and-declared.md)), who owns the list of palettes, how a palette and custom colours inherit, how custom colours are kept readable, and how a per-scope style block fits the Content Security Policy. An addendum of 2026-11-09 asked for one footer line with licence, technologies, version, year and a contact e-mail, a contact that falls back to the quiz's creator, and a side panel of sections on the settings pages that also holds the Basic / All switch.

## Decision Drivers

* Free text and files are not choices; the setting catalogue holds choices
* The domain imports no plugin, and a plugin imports only `app.contracts` ([ADR-0037](0037-providers-and-plugins.md))
* A quiz overrides one field without freezing the others at today's global values
* Every text and background pair stays at WCAG AA ([FR-53](../modules/api-ui.md)), whatever colours an admin picks
* No admin text reaches HTML unescaped or CSS at all
* Only a simple Content Security Policy ([security.md](../security.md))

## Considered Options

* Texts, logo and colours in a domain table; palettes and derivation in the theme; palette and colours resolve as one unit; a nonce for the one style block
* Every field as a catalogue setting
* A per-scope stylesheet served from its own URL instead of an inline block

## Decision Outcome

Chosen option: "Texts, logo and colours in a domain table; palettes and derivation in the theme; palette and colours resolve as one unit; a nonce for the one style block", because it keeps the catalogue for choices, keeps plugins out of storage, and needs no extra endpoint.

Rules:

* **Ownership.** The domain owns the table `branding_configuration` and `app/domain/branding.py` (resolution, validation, saving, the logo through `MediaStorageProvider`, audit). The theme owns the list of palettes and the derivation of a palette from two colours, through `ThemePlugin.palettes`, `branding_fields` and `derive_palette` ([plugin-api.md](../../plugin-api.md)). `color_palette` stays a catalogue setting, with the new choice `custom`; the theme's manifest owns it, as before.
* **Fields.** `name`, `motto`, `logo`, `colours`, `footer` and `contact_email`. Texts exist in cs, en and uk; an empty en or uk text shows the cs one, and a text with every language empty is no override and falls to the next level. Name has at most 80 characters, motto 160, footer 300, all plain text. Built-in values: the name "Kvízotron", the translated motto, a built-in logo that follows the palette (see "Built-in logo families") and no footer.
* **Per-field inheritance.** A quiz overrides each field on its own and follows the global value for the rest, including later global changes; the global value follows the built-in one. Pages that pass `branding_quiz` (play, public quiz, result, walkthrough, scoreboard, projector, preview, test link) use the quiz's branding, every other page the global one.
* **Palette and colours are one unit.** The palette and the two custom colours resolve together from the level that chose `custom`; a quiz that picks a preset takes only that preset, and removing the override returns it to the global custom colours. The colours are saved in the same form as `color_palette` (the settings forms), so choosing `custom` and its colours cannot be saved apart, and `custom` without both colours is refused.
* **Colours.** Accepted only as `#rrggbb`, stored in lower case. The theme derives every token of a palette from the two colours, darkening a main or accent colour in steps until each pair reaches 4.5:1 in light and dark; when it changed a colour, the admin page shows a notice and swatches of the colours used. Only validated hex values and fixed token names reach CSS.
* **Content Security Policy.** `style-src` is `'self'` plus a per-request nonce. The nonce is emitted only on pages that render the `<style>` block of custom colours, so every other page carries no inline style. The alternative, a stylesheet per scope at its own URL, was left out to avoid a dynamic CSS endpoint; it remains the fallback if the nonce proves a problem.
* **Logo.** A replaced or removed logo asset is deleted with `MediaStorageProvider.delete_image` only when no other `branding_configuration` row refers to it.
* **Logo and landing page logo by address (addendum 2026-11-10).** `logo` and `hero_logo` are each set by a file or by an address, for the application and for a quiz (AC-128). An address is fetched with the rules of [ADR-0043](0043-external-images.md), including `allow_internal_image_addresses` and the 25 s limit for one save, and is always kept as a copy: branding has no `external` mode and no background check, since a logo is replaced by editing it. `assets_json` keeps `{asset, source}` per field; a value written earlier is the asset id alone and reads as no source. One save stores every file and fetches every address before it changes anything, then applies both fields in one transaction, so a refused image changes nothing, not even the other one. A file wins over removal and removal over an address; an address equal to the stored one is not fetched again. `branding.set_images` owns this; the form only turns its fields into changes.
* **Changes.** Effective at once, no draft; the audit action `branding.changed` holds field names only, never values.
* **Copies.** Duplicating a quiz copies no branding, like its other setting overrides; archiving keeps it.
* **Built-in logo families (addendum 2026-11-11).** The built-in logo comes in three families, `aurora`, `mint` and `amber`, each as a dark square mark for the bar and a one-line logo with the icons under the text for the landing and quiz pages and the full logo for the About page, each in a light and a dark drawing with a transparent background (`/assets/logo-<family>-{bar,hero-light,hero-dark,about-light,about-dark}.svg`, plain vector). `branding.logo_family` picks the family from the resolved palette: `indigo_pink` and `violet_white` are aurora, `blue_teal` and `green_blue` are mint, `red_plum` is amber, and a `custom` palette by the hue of its derived main colour (amber from 330° through 70°, mint from 70° to 200°, aurora from 200° to 330°). Readability is not left to the choice of drawing, since no drawing suits every page colour: the bar is always dark, so it always shows the dark mark, and the hero logo is a `<picture>` that switches to the dark drawing when the browser prefers dark, with no plate behind it. A logo that was uploaded or fetched is never replaced; a chosen hero logo has no dark twin. The settings pages show which logo applies. The favicon and the touch icon are not part of the families.
* **Large logo visibility (addendum 2026-11-11).** The large logo is shown on `/` and `/about`, and the catalogue setting `show_hero_logo` (Basic, group look, default `on`) can hide it there. Its scope is global only, because those pages belong to no quiz and a quiz override would change nothing anyone sees (ADR-0042). A quiz page shows the large logo only when the quiz has its own (`hero_logo` source `quiz`), so it is hidden by default and uploading it is the switch; a logo inherited from the application is never shown on a quiz page. No logo has a plate: a chosen logo is shown as it is, since its own colours are not ours to guess. A logo set at the application or at a quiz is removed by a button.
* **Organisation on a landing tile and the logo row (addendum 2026-11-11).** A quiz that sets its own name or logo shows them in one small line above its title on the landing page, in both lists (`branding.quiz_marks`, one query for all the quizzes of the page); the global name and logo are the page's own and are never repeated on a tile, and a quiz with neither looks as before. The line is cut off, not wrapped, so a tile keeps its height on a phone. There is no setting: the marks follow from what a quiz already sets. A colour stripe per tile was left out, since a quiz's colour reaches a page only through the one nonce block and the presets' main colours exist only in `theme.css`. The stored asset entry gains an optional `name`, the base name of an uploaded file (at most 80 characters, no path, no control characters); a fetched logo is labelled by its address and an older entry has no label. The settings pages show a set logo as a row with a thumbnail, that label and a small removal button.
* **Footer lines.** Every page that extends `public/base.html` or `admin/base.html`, except the projector view of a scoreboard (AC-83), ends with the footer `_footer.html` of two paragraphs whose parts are joined by " · ". The organisation's line: the admin's footer text · the contact e-mail as a `mailto:` link, left out when both are missing. The application's line: `GPL-3.0-or-later` linking to About · badges Python, Django, HTMX · "Runs on Kvízotron <version>" linking to About · the current year. A missing part is left out with its separator; the Kvízotron line cannot be turned off. (Until 2026-11-09 this was one line; it wrapped at random places, so the parts were grouped by whom they describe.) The version is the installed package's (`importlib.metadata.version("kvizotron")`, omitted when the package is not installed), the year is today's in the configured time zone. The badges are three small text SVGs made for this project (not copied logos), served by the theme from `app/plugins/theme_default/assets/`, each with the technology's name as `alt`; no request leaves the server. Each part is an inline block, so on a narrow screen a line wraps between parts; only a part wider than the screen (a long footer text or e-mail) breaks inside itself.
* **Contact e-mail.** `contact_email` is stored in `texts_json` as `{"cs": address}`, one address for every language, global with a quiz override like the name; it is offered wherever the theme offers `footer`. It must pass Django's e-mail validation and has at most 254 characters; an empty value removes the override. It resolves quiz → global → the e-mail of the admin account that created the quiz; pages without a quiz have no fallback. It is shown publicly, and the form says so. A participant's e-mail is never a source.
* **Admin account e-mail.** `admin_user.email` is optional (at most 254 characters), set when an account is created or later on `Admins`; its help says it can appear in quiz footers. A change is audited as `admin.email_changed` without the value.
* **Quiz creator.** `quiz.created_by` holds the admin id as text, like `question_bank.created_by`. It is set when a quiz is created, duplicated (to the admin who copied it) or created by an import. Migration `domain/0018` fills existing quizzes retroactively: the actor of the oldest `audit_event` with `actor_type="admin"` whose `entity_id` is the quiz's id, else the oldest admin account, else nothing; its reverse is a no-op. A deleted or unknown creator gives no fallback e-mail.
* **Section panel.** Global settings, quiz settings, the run plan and the run page show a panel of links to their sections. On screens of at least 1024 px it is a sticky side panel; narrower it is a floating "Sections" button that opens a `<details>` list. The links are anchors and work without JavaScript; `app/api/assets/sections.js` only marks the current section with `aria-current`. The Basic / All switch of [ADR-0052](0052-setting-groups-levels-and-step-default.md) moves from the admin bar into this panel on those four pages, the ones whose content depends on it; the choice stays in the cookie `kvz_admin_view` and applies on every page.
* **Out of D1.** Editable menu labels and information pages, by decision of the product owner. The public menu keeps its fixed texts.

### Consequences

* Good, because a theme can offer its own palettes and derivation without storage code
* Good, because a global change reaches every quiz that left the field alone
* Good, because unreadable colours cannot reach a page
* Good, because a quiz has a public contact without extra setup when its creator's account has an e-mail
* Bad, because the policy now allows a styled block with a nonce, which must stay limited to the colours block
* Bad, because the palette's `custom` choice and its colours live in two stores (catalogue and table) joined only by the form and by resolution
* Bad, because an admin's account e-mail becomes public on every quiz that admin created and that sets no contact of its own; the help texts on `Admins` and in the branding form say so
* Bad, because the Basic / All switch is no longer on every admin page; it is on the four pages whose content depends on it, and the others do not change with it
