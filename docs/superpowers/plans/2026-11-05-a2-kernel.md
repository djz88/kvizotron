# A2 Kernel Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A kernel that discovers modules through entry points, validates their manifests and dependencies, registers typed ports, enables and disables plugins at runtime, and dispatches events, proven with a separately packaged demo module.

**Architecture:** Discovery runs without Django while settings load and produces `KVZ_MODULES`, which feeds `INSTALLED_APPS` and routes. Everything else (registry, enabled state, audit, events) runs inside a Django app `app.kernel`. Contracts live in `app/contracts`, with no dependency on the kernel.

**Tech Stack:** Python 3.15, Django 6.1.3, Pydantic, packaging, Jinja2, pytest.

**Spec:** `docs/_architecture/modules/kernel.md`, `docs/_architecture/modules/contracts.md`, `docs/plugin-api.md`, `docs/_architecture/data-model.md`, ADR-0004, ADR-0016, ADR-0021, ADR-0036, ADR-0037, AC-01, AC-02.

## Global Constraints

- New runtime dependencies, each pinned exactly in `pyproject.toml`: `pydantic`, `packaging` (version specifiers for `api_compatibility`), `jinja2` (module templates). Use the newest release that installs on 3.15 from wheels.
- `make test`, `make lint`, `make quality` need uv >= 0.13. If the local uv is older, run them in a `python:3.15-slim` container with uv 0.13.7, or run `uv self update` only after the user agrees.
- `app/kernel/discovery.py`, `app/kernel/manifest.py` and `app/contracts/` **MUST NOT** import Django: they run while settings load.
- Tests do not use the network. A module is "installed" for a test by putting a directory with a package and a `*.dist-info/entry_points.txt` on `sys.path`.
- Entry point group: `kvizotron.modules`. Contract version: `CONTRACT_VERSION = "1.0"`.
- Modules do not connect Django signals (ADR-0036).
- Logs contain no answers or personal data; event handler failures log the event name, module id and exception type only.
- IDs of new tables are UUIDv7 (`uuid.uuid7`, ADR-0023), except natural keys given below.

## Decisions this plan makes

The spec leaves these open. All are the planner's calls, not user decisions.

- Provider selection: `KVZ_PROVIDER_<CAPABILITY>`, for example `KVZ_PROVIDER_AUTH=auth.local`. Needed only when more than one provider of an exactly-one capability is installed.
- `REQUIRED_CAPABILITIES` is empty in A2, because no provider exists yet. A3 sets it to `auth` and `persistence`.
- Module routes mount under `/m/<module id>/`.
- `migrations` is removed from the manifest: Django apps own their migrations. ADR-0021 gets a note.
- `plugin_configuration`, `activation_scope` enforcement and `settings_requirements` validation are not built here. The manifest parses those fields; behaviour comes in Stage B and D.
- Kernel does not know quizzes. Domain code registers usage and startup checks through callbacks.
- Event handlers run after commit (`transaction.on_commit`), so a rolled-back operation emits nothing; a handler failure is logged and never reaches the caller (`kernel.md`: submission is independent of event delivery).
- Enabled state is read from the database on each check, without a cache, so a change applies at once.

## Known consequence for A3

`pyproject.toml` has `package = false`, so the project's own entry points are not installed. A3 **MUST** make the project an installable package before adding `local-auth` and `sqlite` as modules. This is left to A3 because A2 has no first-party module.

## Review Focus

- A module package that fails on import: startup aborts and names the entry point, not a bare traceback from an unknown place. Test in Task 1.
- A module installed and the application restarted without `migrate`, or a database never migrated: startup aborts telling the operator to run `migrate`. Test in Task 3.
- A module's `ready()` registering a port that breaks the contract or reuses a key: startup aborts naming the module. Test in Task 2.
- Disabling a plugin that another enabled module requires, or enabling one whose dependency is disabled: refused with an explanation. Test in Task 3.
- An event handler that raises: the operation succeeds, other handlers still run, and the log contains no event payload. Test in Task 4.
