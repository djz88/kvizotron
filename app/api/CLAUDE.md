# Module: app/api

Thin views and pages: converts a request into a call of a service in `app/domain/` and the result into HTML. The rules are not here.

## Responsibilities

- Public pages: `public.py`. Playing: `play.py` (start, resume, submit, time, entering the code), `play_errors.py` (rejection codes with a status and text, the error page, `_limited`) and `play_switch.py` (check, revision-status, switch; the routes in `app/urls.py` point here). `assets/resume.js`: a copy of an attempt in progress in `localStorage`, only an enhancement. `rate_limit.py`: request limits per IP in process memory, five buckets (`login`, `login_address`, `code`, `submit`, `start`) in a sliding minute (`login` and `login_address` are taken by `admin_auth.login_page` through `rate_limit.try_acquire` before `authenticate()` with a key of name and address, respectively address only, and on a correct login it returns them through `release`, so they count only failures; `code` only wrong codes in `play.py`); `submit` and `start` are counted by `play._limited` as the first thing in the view (`start` every request, `submit` every attempt once per window: within a minute of the first counted submission of an attempt from an address, at most 8 of its repeats (`FREE_REPEATS`) pass without a slot through `rate_limit.try_acquire_once`, a repeat does not extend the window and the ninth counts as a new submission, ADR-0058; a rejection is 429 with `Retry-After`), `check`, `resume`, `switch` and time are not limited; the client address is the N-th value of `X-Forwarded-For` from the right, N = `KVZ_TRUSTED_PROXIES` (default 1: Caddy or the ingress; the value appended by the outermost trusted proxy; 0 means `REMOTE_ADDR`), without it `REMOTE_ADDR`, empty is `unknown` (ADR-0066).
- The start and submit forms have `?lang=` in `action` and `hx-post` (except submission in the preview in the administration, which would switch the admin's language), so the 429 is in the form's language; `assets/countdown.js` repeats the automatic submission after a connection error and 5xx (after 1, 1, 1.5, 3, 6 and 12 s; only a repeat within the 5 s reserve before the end saves it, the server rejects everything after the limit; no request timeout, a hanging request is not repeated) and after 429 by `Retry-After` (60 s, at most twice, always after the limit), always with the same submission key, never `start`; `assets/number.js` only warns about the shape `1,000` and blocks nothing (ADR-0060).
- `heartbeat.py`: `HeartbeatMiddleware` (last in `MIDDLEWARE`) writes the `app` heartbeat at most once per 10 s per process on any request including `/healthz`; a write failure is logged by type and the response does not change; on a clean process exit the file is deleted (`atexit`). It is read by `restore`; the deletion history ("Deletion history") shows the last `jobs` pass (`heartbeat.read_pass`, ADR-0061).
- Test links: `public.test_link`, `admin_links.py`. Preview: `admin_preview.py` on the `public/` templates. Import and export of questions: `admin_import.py`, `admin_export.py`. Results export: `admin_results_export.py` (`/admin/exports/…`, templates `admin/results_export.html` and `admin/_export_jobs.html`) and `export_runner.py` (a background thread, ADR-0055).
- Administration: `admin_*.py`, routes in `admin_urls.py`, forms in `admin_forms.py` and in the modules that were split off from it and from which `admin_forms` re-exports them: `admin_forms_quiz.py` (quiz, settings and shared helpers), `admin_forms_branding.py` (look and colours), `admin_forms_rewards.py` (rewards).
- `pass_mark.py` assembles the pass-mark rows for the result, the private link and the preview (AC-172); "Attempts left: %(count)s" and the messages about used-up attempts are in `play.py` and `public.py` (AC-173).
- `rendering.py` draws pages and questions, `i18n.py` chooses the language, `jinja.py` is the template environment.
- Templates: `jinja2/admin/`, `jinja2/public/`. Own catalog in `locale/`. Public pages inherit `public/base.html`, quiz pages in the administration include `admin/_quiz_header.html`.

- Name edited in place (AC-160, AC-161): `inline_name.py` (`NameField`, `wants_partial`, `render_field`), the macro `admin/_inline_name.html` and `assets/inline-edit.js` (Enter, Esc, focus; without it the `?edit=` link works). The place only supplies addresses and fields, the domain saves; a rejection is 400 with the field and the written text both for HTMX (partial response) and without it (whole page). `NameField.mirror` is the id of an element whose text is overwritten out of order after saving (`hx-swap-oob`), `bare` draws only the pencil. A new name needs a route with GET and POST, a `uuid` argument in `ARGUMENTS` of the limits test and `{{ csrf_input }}` (the macro is imported `with context`).
- Bar above a list (AC-170): the macro `admin/_list_bar.html` (`{% call list_bar(name, count, note) %}` with buttons `role="button" class="secondary outline"`). Import, replacement and download of a list belong only in it or in `.page-title`; a link to `admin_import_new` or `admin_*_export` elsewhere is rejected by `tests/api/test_list_bar.py`, as is the old `<p class="row-actions">`.
- Errors of a whole form are drawn only by the macro `admin/_form_errors.html` (`form_errors(form)`: a `notice form-errors` box with `role="alert"`); a bare `non_field_errors()` in a template is rejected by `tests/api/test_run_plan.py`. The run plan returns 400 for an invalid field and 409 for a rejection by the rules (also "Start now"). Unpublished quiz: "Plan…" leads to publishing with `?then=plan`, which after publishing goes to the plan, and the plan page offers "Publish and plan a run" instead of the form. The address of the QR code and the public link is assembled by `admin_runs._public_url` from `Quiz.public_origin`, otherwise from the request address; the `public_origin` field is on a new quiz and in the quiz settings (ADR-0067).
- `admin_workspace.py` builds the quiz header, the rule for the main button is in `app/domain/quiz_state.py`.
- Quiz type (ADR-0062): `admin_quiz_types.py`. `admin_quiz_type` (`quizzes/<id>/type`) GET `?type=` and also POST without `confirm=1` show an overview (`admin/quiz_type_confirm.html`: changes, edits, skipped keys, content warnings and, for a run that the type changes, the `flow_choice` choice from `_run_flow_choice.html` inside the form), POST with `confirm=1` applies the type (without a `flow_choice` answer the overview with 400, `FlowRefused` 409, nothing is written; `admin_quiz_type_remove` does not ask), a rejection is the overview with the message of the settings form (`admin_forms.clash_message`) and 409, an unknown or disabled type 404; `admin_quiz_type_remove` (POST) forgets the type. The bar `admin/_quiz_type_bar.html` above the quiz settings (`admin_workspace.type_bar`, choosing a type is GET) and the `▲` marks at deviations (`type_marks` through `_setting_groups.html` into `setting_row(mark=…)`; a deviation stays visible in the Basic view too). A new quiz has the types in a closed `<details class="quiz-type-choice">`, the type is applied only after the quiz is created.
- Saving the quiz settings (`admin_quizzes.quiz_settings`) asks whether a change of walkthrough, reveal, shuffling or sources is taken over by a scheduled or open run (ADR-0069): `run_flow_change.settle` at the end of the transaction, without a `flow_choice` answer nothing is saved and the page `admin/quiz_settings_confirm.html` returns the entered fields together with the choice (`run_offer_context` fills `_run_flow_choice.html`, shared with the quiz type); a run that does not accept the change offers only `next`.

## Forbidden

- Importing from `app/plugins` and `app/providers`: plugins are taken from the registry through `registry.get`.
- Deciding about the score, revisions or the state of a run: the domain does that.
- An admin form without `{{ csrf_input }}` and a new `csrf_exempt` route other than `start`, `resume`, `submit`, `check`, `attempt_time`, `switch`: guarded by `tests/api/test_request_limits.py`.
- A public route that accepts POST without a row in `LIMITS_OF_ROUTES` (the bucket `login`, `login_address`, `code`, `submit`, `start`, or a reason that it needs no limit): `tests/api/test_request_limits.py` fails.
- An inline script or style: CSP does not allow them. The only exception is the block of custom colours in the theme layout with a `nonce` (`style-src 'self' 'nonce-…'`, ADR-0054); `csp_nonce` is read only on the page that draws that block, otherwise the nonce is not added to the header.
- Sending a participant anything other than `public_payload()`.

## Watch out

- HTMX attributes are inherited: an element inside `<form hx-target>` needs its own `hx-target` and `hx-disabled-elt`.
- Texts in `admin*` files and templates are cs and en, the others also uk (`tests/test_translations.py`).
- A theme may override any template, because it is loaded before `app.api`.

- The public quiz page passes `branding_quiz`, otherwise `page()` uses the global name, logo, colours and footer. The administration never passes it. No text from an admin belongs in `<style>` or `<title>`, only a verified `#rrggbb` colour and fixed token names. The colours `main` and `accent` are in the settings form of the quiz together with `color_palette` (one POST, `require_colours`); `BrandingForm` (multipart) holds only texts and logos, each by a file or an address (`logo_source`, `hero_logo_source`): `_image_changes` only picks for each field a file, a removal, or an address (in this order) and `branding.set_images` changes them all at once or not at all; a rejection carries the field to be marked (`ImageChangeRefused`).
- The footer is `_footer.html`, included from `public/base.html` and `admin/base.html`: two paragraphs, the organisation line (footer text, e-mail; both missing means the line is missing) and the application line (licence, badges, "Runs on Kvízotron", year). Each part is a `<span class="site-footer-part">` that does not wrap. `page()` gives it `app_version` (`importlib.metadata`, empty without an installed package), `footer_year` in the configured time zone and `footer_badges` (badge addresses from the theme). A new footer part belongs in the right line with the separator " · " and a missing part is left out together with its separator. The contact e-mail is public and comes from `branding.contact_email`, never from a participant.
- The `contact_email` field in `BrandingForm` is only where the theme offers `footer`. "Admins" (`admin_users.py`) has two forms at one address: a new account and a change of e-mail, distinguished by the field `admin_id`; the audit `admin.email_changed` is without the address. The login is changed with the pencil (`admin_user_login`, `?edit=login-<id>` without JavaScript), a new password, blocking and deletion have their own addresses under `admins/<id>/` and call the rules from `app.domain.admins`; a rejection is a message at the top of the page (409 own account and last admin, 400 invalid input), deletion asks through `confirm.html` (AC-169).
- The section panel `admin/_section_panel.html` is on `admin/settings.html`, `admin/quiz_settings.html`, `admin/run_plan.html` and on every run tab (`admin/_run_tab.html`) and holds the "Basic" / "All" switch; it is no longer in `admin/base.html`. The links are anchors (`#group-<key>` and `panel_before`/`panel_after`), so a new page section needs an `id` and an entry in the panel. `assets/sections.js` (in `SCRIPTS`) only marks the current section with `aria-current`; without it the panel works. Parts of a run are pages, not anchors (ADR-0068, the rule in `docs/_architecture/modules/api-ui.md`): the tabs "Overview", "Attempts", "Scoreboard", "Statistics", "Rewards", "Draw", "Export" and "Settings" have their own address and above the content `admin/_quiz_header.html` and `admin/_run_header.html`; what is in the bar is decided by `run_tabs.shown` (the current tab always). A link to a part of a run is `url('admin_run_<tab>')`, never `admin_run` with `#`; a form returns to its tab and a POST has a verb or `…/settings` (`admin_run_scoreboard_settings`). `#` jumps only within one page (e.g. on the Settings tab `access-code` and `data`).
- Menus are `<details open>`. `assets/nav.js` closes them on a narrow screen, without JavaScript they stay open.
- Files from the question editor are saved by `_form_with_uploads` before the form reaches the plugin. Multipart elsewhere than there and on `/admin/import/new` is not possible (`RefuseMultipartMiddleware`).
- `assets/sortable.js` and `assets/editor.js` only enhance: without JavaScript the order is a list with a choice of positions and submission still works.
- `#play` also contains the heading of the quiz page, so that starting replaces it. The card is only in `_questions.html` and `_result.html`.

## Public API

None for other modules. `not_archived` and `edit_page` from `admin_quizzes.py` are used only by `admin_revisions.py`, `admin_runs.py` and `admin_quiz_types.py`; `admin_quiz_types.py` takes `run_offer_context` from it too. The button "Use: %(value)s" at a module requirement (`requirement_use`) asks the run like saving settings: it shares `_run_question` and `quiz_settings_confirm.html` (`action`, `back`), "Cancel" leads to an allowed `next`, otherwise to editing the quiz.

Profile `none`: after submission the attempt does not exist, a token without a row gives `attempt_gone` (410) without a score. Resume takes the token only in the POST body and does not need the cookie with the code; a rejection after which the copy makes no sense carries `X-Kvz-Drop-Copy`.

The switch and groups: `admin_view.py` holds the cookie `kvz_admin_view` and `group_fields`, which the settings pages and the run plan draw through `admin/_setting_groups.html`; the switch is in the section panel. A hidden field is not submitted: saving must take an empty value as "no change" (ADR-0052). Tests of advanced fields use the fixture `showing_all`. The order within a group is alphabetical by the translated label and a dependent setting stands indented under its parent (`CHILD_OF`); a choice with at most three values is a row of switches. Search (`?q=`, `query` in `group_fields`) only marks non-matching fields `hidden`, never omits them, otherwise saving would delete the quiz override (AC-168).

Scoreboard: `scoreboard.py` draws `/q/<slug>/r/<run>/scoreboard` and the fragment `/rows`, which HTMX refreshes every 15 s until `board.final`. The language is activated before the reasons for hiding are built. The projector (`?view=projector`) is only the scoreboard: the template empties the layout blocks `header` and `footer` and has no links or buttons; links to it have `target="_blank" rel="noopener"`. The own place in the result is given by `scoreboard.place_context`.

Participants: the cookies `kvz_p_<run>` and `kvz_c_<run>` are set only by `play.py`. On a locked run the code is checked before the name or the participant. A response that returns the written name or e-mail has `private, no-store`; `/v/<token>/identity` rejects with 200.

Rewards: `admin_rewards.py` is the quiz tab "Rewards" (template `admin/rewards.html`) and the run tab "Rewards" with claims and manual awarding (`admin/run_rewards.html` on `admin/_run_tab.html`); the shared sections are in `admin/_rewards_sections.html`. It changes the structure of a rule only for a scheduled run, otherwise it saves only texts; it converts `RewardConflict`, `RuleLocked` and `RuleInvalid` to messages. The run tab "Draw" (`/admin/runs/<id>/draw`, template `admin/prize_draw.html` on `admin/_run_tab.html`) changes nothing on GET; the actions are POST and `DrawRefused` is converted to a sentence (409, a missing reason 400). The winner's e-mail is only on the rewards and drawing page of the run. Scheduling and opening a run in `admin_runs.py` and `admin_quizzes.py` catch `RewardConflict` the same way. Publicly: the own rewards at the result and on `/v/<token>` are given by `play.rewards_shown`, the reward names on the quiz page by `public.py` and the published winners by `scoreboard.py`, also for a hidden scoreboard, only on page load, not in the `/rows` fragment.

Grading, photos and results: `admin_grading.py` is the tab "Grading". `/v/<token>` and `/q/<slug>/r/<run>/answers` answer 200 with one message and a rejected photo 204, so that neither the token nor the existence of a photo gets into the log. That is why `result_photo` has two routes (`v/<token>/photo/<path:answer_id>` and `v/<token>/photo/`, the same name): the rest of the path is text, the view verifies it as a UUID and answers 204 for anything else, because a 404 would log the path with the token. What anyone may see is decided by `app/domain/visibility.py`, not the template.

Results export (ADR-0055): `admin_results_export.py` takes the provider through `export_runner.provider()` (`registry.get("results_exporter", "csv")`), offers files according to `results_export.offered` and rejects a file with personal data or photos (only in a ZIP with the answers file) without `personal_ok` with 400, keeping the choice. It writes the job and the audit `export.created` in one transaction, `kick()` only after it. `export_runner.kick()` calls `claim_next()` as long as it returns a job and starts each through `SPAWN` (by default a daemon thread `kvz-export`; tests replace it with a synchronous call, because the in-memory test SQLite does not see another thread). When the thread cannot be started, the job gets `fail` and the slot is released. `_run` writes the files or calls `fail(…, "error")` and logs only the job id, then `kick()` and, as the very last thing, `connection.close()`, so that no open connection remains after the thread. `kick()` also runs on page load and on every query of the `/admin/exports/jobs` fragment. The download has `private, no-store` and writes `export.downloaded`. It takes the run state from `run_tabs.status_label`.

Modules (ADR-0057): `admin_plugins.py` is the list of modules and the detail (`/admin/plugins`). It takes the reasons for rejection from `lifecycle.blockers` and has no rule of its own.

Data deletion (ADR-0056): `admin_retention.py` is the deletion history "Deletion history" (`/admin/retention`, `?page=` by 200 rows, `?run=` one run), held runs, the erasure request, e-mail verification and "Delete data now" (`/admin/runs/<id>/delete-data`). `app/domain/retention.py` decides and deletes, the view only calls and translates. The entered e-mail travels only in the POST body and a response that may show it has `private, no-store`. The deletion date is drawn by `admin/_deletion.html` with colour and text, so a new theme must have `.deletion-soon`. A deleted run is, for the public pages, an unavailable state `data_deleted`, not an error.
