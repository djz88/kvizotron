# Module: app/domain

Quiz, revision, run and attempt: models, their rules and the services the views call. The terms are defined by `docs/_architecture/modules/domain.md`.

## Responsibilities

- `models.py`: `Quiz`, `QuizRevision`, `QuizRun`, `RunRevision`, `Attempt`, `Participant`, `AppSetting`, `QuestionBank`, `BankFolder`, `BankQuestion`, `RewardRule`, `RewardEntitlement`, `Draw`, `DrawEntry`, `BrandingConfiguration`.
- `authoring.py`: draft, publishing, returning, discarding, runs, duplication (copies `quiz_type` and all overrides of the quiz settings, not the look; the title gets "(copy)", "(copy 2)" in every language), archiving. The quiz title is unique in every language among quizzes outside the archive (regardless of case and spaces, `taken_titles`, `ensure_title_free`, `free_title`, exception `TitleTaken`; only a title that is being changed is checked, `new_titles`, so older identical titles lock nothing; both the copy and the numbered title fit into `MAX_TITLE` 200); every new place that writes a title must pass `ensure_title_free` (with `new_titles`); it is guarded by returning to a revision, discarding a draft, restoring from the archive and duplication, the forms and renaming in `app/api` and the import, which numbers an occupied title "(2)" with a notice (ADR-0067). `Quiz.public_origin` (migration `0027`) is the beginning of the address of the QR code and the public link, empty means the admin's address.
- `attempts.py`: start, submit, switching an attempt, score; it passes the number of started attempts and "no more after success" to the participant rules (AC-173), `LATE_UPLOAD_WINDOW` is a 10-minute window after a run is closed. `reveal.py`: the state of answers and `is_shown` with the allowed moments; `after_close` shows from `closed_at` plus the window (AC-175). `tokens.py`: the signed attempt token.
- `run_schedule.py`: the run plan, what time made due (`settle`), the deadline, archiving, unsubmitted attempts (ADR-0048). `clock.py`: reading and displaying time in the configured zone, `iso()` for files (ISO 8601 with the zone offset).
- `banks.py`: question banks; the difficulty of a question is the reserved label `easy`, `normal` or `hard` (`normal` without it, decided when the pool is built, labels are not overwritten; more than one level is an error, `check_one_level`), a draw row carries `difficulty` (ADR-0041, AC-163). `bank_folders.py`: bank folders (a tree of at most four levels, one folder per question, only an empty one can be deleted), counts with subfolders, search regardless of case and diacritics and bulk move; a draw row refers to a folder by id (ADR-0041). `selection.py`: which questions an attempt gets, drawing without repetition. `questions.py`: what every stored question has. `reveal.py`: what a participant is told about a question.
- `settings.py`: application settings (question → quiz → global value → default, ADR-0042); each has a `group` and `level` only for the administration pages (ADR-0052). The default walkthrough is per question, migration 0015 leaves an existing installation on "all at once". `external_images.py`: from which addresses a quiz really loads images.
- `preview.py`: preview without saving (an unsaved `Attempt` from a signed token). `run_links.py`: test links (ADR-0044); `set_origin` stores for one link only the displayed beginning of the address (`clean_origin`: http/https, host or IP, port), the audit without the address and token (AC-167).
- `question_import.py`: what the import rows mean (target `bank` with `replace` first saves the new questions and then deletes those the bank had before the import, in one transaction; a bad row makes the plan reject it, a save failure raises `ReplaceRefused`, folders and bank ids stay; AC-165; `Placement` from the check form overrides the top level of the file's paths in `interpret` before the plan is judged, AC-166), `import_structure.py`: what the import check into a bank shows (the folder tree with "existing folder" / "new folder" and the draw rows that would lack questions after replacement, counted as in the editor), it only reads; `question_export.py`: what the downloaded file contains (ADR-0045).
- `grading.py`: what a person decides about a stored answer, recalculating the score. `visibility.py`: who may see an answer and a photo, pages ask only here. `walkthrough.py`: the public walkthrough during (ADR-0046, ADR-0047). `requirements.py`: module requirements on settings (ADR-0034); `unmet(..., values=)` judges a key by the given value (a run by what it holds, ADR-0069), `apply(..., flow_choice=)` is a change of the quiz settings like any other and asks the run through `run_flow_change.settle`.
- `setting_rules.py`: which quiz settings do not go together (`clashes`, `Clash` with a reason and a field, `ADJUSTABLE`), rules of the settings forms and of the quiz types; a missing or empty value is global. `clashes` does not look at runs, clashes with run values are given by `run_clashes(run, values)`. The message texts are in `app/api/admin_forms.py`.
- `run_flow.py`: the seven walkthrough values that a run carries in `QuizRun.flow_json` from scheduling or opening (`KEYS`, `snapshot(quiz)` from the quiz, `of(run)` the stored values, `flow(run)`; ADR-0069).
- `run_flow_change.py`: a change of these values on the quiz offered to a scheduled or open run (`offer_for`, `Offer`, `settle` as the last step of the transaction that wrote the quiz; `ChoiceNeeded` and `FlowRefused` roll it back; the field `flow_choice` with `run` or `next`; accepting the change during the run writes the audit `run.flow_applied` only with keys). `authoring.publish` leaves a run (open and scheduled) on its revision also when its held values do not satisfy the requirements of the new revision (`_held_reason`, next to the rule for a run without saving with a photo); `held_back(quiz)` returns the reason (`stateless` or `requirements`) for an open run, which the page tells about after publishing.
- `quiz_types.py`: applying a quiz type (ADR-0062): types from the port `quiz_type` (`available` only enabled ones by `order`, `get` also disabled ones), `preview` and `apply` (the type's values as overrides on the quiz and `Quiz.quiz_type`; when the type changes, keys of the old type that the new one does not set return to the global value, `basic` deletes all overrides; a key of a disabled module is skipped; a clash with another setting is corrected by `setting_rules.ADJUSTABLE`, other clashes make the type be rejected by `TypeRefused` and nothing is written; content that does not go with the type only warns; `Preview.run_offer` offers a change of the run instead of the earlier warning, `apply(..., flow_choice=)` handles it through `run_flow_change.settle`), `apply` recomputes the preview in the transaction and audits `quiz.type_applied` with the type id; `remove` forgets the type and leaves the values (`quiz.type_removed`); `deviations` compares with the current definition of the type.
- `usage.py`: why a module cannot be disabled (`Blocker`); an open and a scheduled run and live reward rules.
- `data_policy.py`: the data profile and retention period on a run (`retention_json`), what `none` excludes (ADR-0050). What an attempt stores is decided here; `attempts.effective_profile(run)` also applies to a test run.
- `plugin_overview.py`: where the value of a module setting differs from the global one (D4); it reads the draft, otherwise the last published revision, and leaves out archived quizzes.
- `retention.py`: deleting a run's data (D3): one path for the period expiring and for "delete now" (`purge_run`, `delete_now`), in short transactions; the summary with counts is stored first, so an interrupted deletion resumes and writes one record. `run_stats` reads a deleted run from the summary (`retention_summary_json`). `run_pass` is the hourly pass (it also finishes an interrupted deletion of a run that is otherwise not due) and `sweep` deletes private photos without an answer older than an hour; they are started by `management/commands/retention.py` and the `jobs` service (`management/commands/jobs.py`). Erasure across runs: `search_email`, `search_name`, `erase` and `fingerprint`, an HMAC of the e-mail in the erasure record (the address is not stored there anywhere). `search_email` searches by `Participant.email_key` (the address after `strip` and `casefold`, `participants.email_key_of`, set by `claim_name`, migration `0020` fills in old rows), with one query; the key is personal data like the address and is deleted with the row. After the commit `erase` clears the scoreboard cache of every affected run (`results.clear_board_cache`). The deletion summary also holds `trigger`, `admin_id` and the marker `late_exports_pending` until the late removal of exports has succeeded (`run_pass` tries it for 24 hours), `_leave_summary` subtracts the erasure rows and `run_pass(now, stop)` reads `stop` before every run (ADR-0061). Held runs (`retention_held_at`, migration `0019`) are deleted only by `release_held`, `run_schedule.set_period` rejects a shortening into the past without confirmation (ADR-0056). When a run is due is in `data_policy` (`deletion_at`, `is_due`, `deletion_soon`).
- `backup.py`: the daily backup of the database and media (D5): `create` builds `.tmp-<date>`, copies the database with the SQLite backup API in 100-page steps (never by copying the file), links unchanged media files with a hard link (only when the file in the previous backup matches the manifest, a damaged one is copied from the live media) and does not back up the directories `exports` and `imports` under the media, which live for hours (`TRANSIENT`), verifies (`verify`: `integrity_check`, sums from `manifest.json`, migrations known to the installed code) and only then renames to `YYYY-MM-DD` (local date); before the rename it writes everything to disk (`fsync` of files and directories), the database copy has the deadline `DATABASE_COPY_SECONDS`; a failure of any kind deletes the directory, only the exception type goes to the log and a `BackupError` with a fixed text is raised (also in `prune`, which takes the same lock). `listing` does not see `.tmp-*`, `due` asks about the local date, `prune` never deletes the newest valid backup and also deletes `pre-restore*` and returns `PruneResult` (`removed`, `stayed`); when a directory is left over, the `backup` command prints the count to stderr and ends with an error, `jobs` logs only the count (the pass stays `ok`). The `backup` command is in `management/commands/backup.py`. `restore` (command `management/commands/restore.py`, `resolve` picks `YYYY-MM-DD` or `latest`): verifies the backup, refuses an older schema (a migration of the installed code is missing) and a currently open connection to the database (`BEGIN EXCLUSIVE` with a short deadline and, after closing its own connection, also a leftover `-wal` or `-shm`, because a reader in WAL mode does not hold the lock; before that it refuses while the `app` or `jobs` heartbeat next to the live database is younger than 60 s, because an idle running service holds no connection; ADR-0061), takes the lock as `create` does, copies the existing data into `pre-restore-<time>` and then swaps the content in the database and the media, never the directories (they may be volumes) nor `exports` and `imports` under the media (it neither backs them up, nor cleans them, nor stores them in `pre-restore`) and never by a hard link (media files share inodes with other backups); after a complete `_stash` and before `_install` it writes the marker `.restoring` (`MARKER`) into `pre-restore-<time>`, deletes it after a successful `_install` and after a successful `_put_back`, and a new `restore` refuses while any marker exists (the directory name is in the message); `prune` never deletes a marked directory; on an error it returns the original data, `chown` to uid 1000 only as root, otherwise a possible warning. The `restore` command does not run system checks (`requires_system_checks = []`): they open a connection to the live database and restore would take them for another user. The `jobs` service is driven by `pass_once` (`management/commands/jobs.py`): `retention.run_pass`, `admins.clear_expired_sessions`, then, unless `stop` is set (otherwise the pass ends as `stopped`, or `failed` when something has already failed), and when it is `due`, `create` and `prune`, each in its own `try` (a failure of one does not stop the other, the exception type goes to the log); `prune` also runs after a failed `create`.
- `management/commands/serve.py` (ADR-0066): one container (target `single` in the `Dockerfile`): first it creates the database directory (`prepare`, an empty volume does not have it), `migrate`, then gunicorn (`GUNICORN` = `IMAGE_COMMAND`, i.e. the image's `CMD`, plus `--keep-alive 75` so that idle connections survive the ingress) and `jobs` side by side; SIGTERM goes to both and the deadlines of 30 and 115 s run from the same moment, then kill; a stop during migration starts nothing; the exit of either ends the container with its code (0 becomes 1, signal N becomes 128 + N) and a child that cannot be started stops the others. Compose does not use it.
- `heartbeat.py` (ADR-0061): hidden files next to the database file, the `app` and `jobs` heartbeat (`beat`, `age`, `clear`, `STALE_SECONDS` 60) and the record of the last `jobs` pass (`write_pass`, `read_pass`: start, end, result `ok`, `failed` or `stopped`; `jobs_healthy`). Reading only from the standard library, a write never raises an exception, without a file database it does nothing. `python -m app.domain.heartbeat check` is the healthcheck of the `jobs` service (it fails when the `jobs` heartbeat is older than 45 s (3 × `JOBS_INTERVAL`), no pass is running and the last ended more than 7200 s ago, or a running pass started more than 3600 s ago; the running one is the one whose start is newer than the last end). `app` writes the heartbeat from `app/api/heartbeat.py`, `jobs` from a thread every 15 s and `pass_once` writes the record; a pass after which `prune` left directories stays `ok`.
- `participants.py`: participant rules on a run, the cookie hash, who may start or continue, name and e-mail, the attempts table. `find_or_create` gives a new participant a `number` from the counter `QuizRun.participant_seq` (raised by `F() + 1` in its own `IMMEDIATE` transaction; the counter only grows, so the number of a deleted participant is never given to anyone again; unique within the run, migration `0024` numbered older rows and set the counter); the number of an anonymous name never changes, not even after another participant is erased. A new place that creates a participant must assign it the same way. `access_codes.py`: the access code only as a hash, and the unlock token (ADR-0049).
- `results.py`: the scoreboard settings on a run (`results_json`, `seed`), conflicts, the scoreboard (`board`, `place_of`, `is_public`, ADR-0051); the revision mode `percent` (default, one table by percentages of the maximum of the attempt's own revision, `Table.max_score` is `None`), `separate` and `latest`, changed on a run through `set_display`, and it also decides which attempt counts (`kept`, ADR-0065). A shared scoreboard of several runs: `share_board`, `split_board` and `shared_runs` (`QuizRun.board_main`, migration `0026`, rejection `ShareRefused` with the codes `too_few`, `other_quiz`, `test_run`, `already_shared`, `main_is_member`, audit `run.board_combined` and `run.board_split` only with run numbers); the main run shows in `_build` (publicly and to the admin) one table by percentages, each run filtered by its own revision mode and with its own official-attempt rule, with the tie rules of the main run, pending grading in any run holds it back (also in `is_public` and `public_runs`), an anonymous name carries the run number and for the admin every row carries it; publicly it omits the rows of a member whose own scoreboard is hidden as `archived` or `data_deleted`; `_forget` of a member also deletes the cache of the main run; `place_of`, `kept`, rewards and drawings stay within one run. The number of an anonymous name is read by `_numbers` from `Participant.number`; an attempt without a participant (and a participant without a number) goes after the highest stored number in order of arrival. `kept` (ADR-0063) gives the attempt and the numbers that count (first, best, last, average, AC-174; it picks like the scoreboard by the run's revision mode, for the average the numbers are the average of points and the average of maxima; only submitted attempts with scoring are counted, `waiting` is only a flag for the pass mark), `official_attempt` is its attempt. `pass_mark`, `judge`, `attempt_passed` and `kept_passed` give the pass mark from the values copied into `results_json` (nothing is stored, AC-172). The order and ties are computed by the `result_view` plugin. `run_stats.py`: run statistics and run comparison, `of_revision` by revisions and the public `question_max`.
- `rewards.py`: the reward settings on a run (`rewards_json`), the reward rules of a run and the quiz template (a rule without a run), copying rules when scheduling or opening by `reward_source`, conflicts (`profile`, `reveal`, `contact`). The structure of a rule can be changed only on a scheduled run and in the template, texts at any time. Claims (`refresh`) from the numbers of `results.kept` (the claim's attempt is `kept.attempt`, for the average the last submitted) in the submission and grading transaction; `refresh_run` recomputes every participant of the run with a finished attempt in a transaction that changed the revision mode (`results.set_display`) or switched the run to another revision under `latest` (`authoring._move_round`, not with `stay`; only that mode filters by revision), and leaves finished drawings alone; the recomputation cancels only automatically granted and not handed over claims and never grants again what an admin cancelled; manual granting, handing over and cancelling with a reason are in the audit without names (ADR-0053).
- `draws.py`: a prize drawing for a `draw` rule (FR-37, FR-38, ADR-0013): a preview of eligible participants, `refusal` (why a drawing would not pass now, it only reads), the drawing, moving a substitute up, a substitute winner, a new drawing and publishing winners. Only for a closed or archived run without pending grading and outside profile `none`; every step is a new `Draw` row, the old one never changes, the audit carries only pseudonyms (`pseudonym`: a salted HMAC-SHA256 of the participant id). Moving up takes the first substitute who is eligible now; a skipped one keeps their place. Claims from a drawing are written by `rewards.py`.
- `branding.py`: the name, motto, logo, colours and footer of pages: a global row and per-field overrides on a quiz, texts cs/en/uk (an empty en and uk takes cs, all empty lets through to the next level), the palette `custom` and its colours are taken from the level that selected it, the logo through `MediaStorageProvider` (`assets_json` holds `{asset, source}`, an older value is a bare id; `set_images` changes both logos at once, a file or an address as a copy, or removal: it first stores all files and downloads all addresses within one limit `external_images.FETCHES_SECONDS`, then writes in one transaction, so a rejected image changes nothing) and a file is deleted only when no other row uses it, the audit `branding.changed` carries only field names (ADR-0054). The contact e-mail (`contact_email`, in `texts_json` as `{"cs": address}`) has the order quiz → global → the e-mail of the quiz author's account; without a quiz it is not filled in.
- `admins.py`: renaming, password, blocking and deletion of an admin account (AC-169, ADR-0014). Your own account and the last active admin cannot be blocked or deleted (`OwnAccount`, `LastAdmin`); blocking, deletion and a new password delete the account's stored sessions (`end_sessions` reads only valid sessions, a new password of one's own leaves the current one); expired sessions are deleted by `clear_expired_sessions` in every `jobs` pass. The audit carries only the account id.
- `creator.py`: the e-mail of the admin who created the quiz (`Quiz.created_by`); empty when the author is missing, was deleted or has no e-mail.
- `results_export.py`: what a run exports (FR-42, ADR-0055): `offered` by data profile, `tables` as `ExportTable` (attempts, participants, question statistics, answers, claims, drawings; every row starts with `run` and `revision`), `photo_files`, `file_name`, audit `export.created` and `export.downloaded` without values. It takes the place from the run's own scoreboard for the admin (`results.board(audience="admin", own_run=True)`, `BoardRow.attempt_id`; a shared scoreboard of several runs is not counted), the official attempt from `results.official_attempt` (for the average every attempt the run counts, `results.counted`). The text of an answer is given by `summarize` of the question type.
- `revision_diff.py`: comparing snapshots for the change overview.
- `usage.py`: which modules need open runs.

## Forbidden

- Importing from `app/api`, `app/plugins`, `app/providers`: the question type and scoring go through `registry.get`.
- `save()` on a revision that is not a draft: `QuizRevision.save` rejects it. State is changed only by `.filter().update()`, content never.
- Re-evaluating or moving an existing attempt to another revision: switching creates a new attempt.
- Editing an archived quiz: services start with `ensure_editable`.
- User-facing strings without `gettext`. The domain has its own catalog in `locale/`.

## Watch out

- `title`, `supported_locales` and `default_locale` live until publishing on the `Quiz` row, not in the draft. The draft holds only questions and draw rows (without the pool: that is created at publishing).
- Transactions are `IMMEDIATE`, so a check and a write in one `atomic()` do not race. `with_retry` handles only the SQLite lock.
- Neither answers, the test-link token, the access code, a name nor an e-mail belong in the audit or the log.
- The check of repetition and of the same name belongs in the same `atomic()` as the write of the attempt. An `ABANDONED` attempt is rejected by every input with a token.
- `QuizRun.objects` and `quiz.runs` do not see test runs and `QuizRevision.objects` does not see test copies; whoever wants them calls `all_kinds`. A query on `Attempt` across runs must filter the run kind itself.
- Under profile `none` an attempt is deleted at submission together with the `replaced_by` chain and the count grows in the same transaction; a test run does not raise it. The duration is stored only under `detailed`.
- Older attempts still have `store_answers` in `settings_json`; it is read by `data_policy.profile_of_attempt`.
- The participant cookie is decided by `participants.needs_participant(run)`: the run's rules, a visible scoreboard, or reward rules. The public scoreboard is cached for 5 s (`kvz-board:<run>:<language>`); tests clear it in `tests/conftest.py`.
- The official attempt for rewards, drawings and the pass mark is picked by `results.kept` (`official_attempt`) the same as the run's scoreboard (TD-047): with `percent` and `separate` from all revisions by percentages of the maximum of the attempt's own revision (`_pick_by_percent`, `_maxima`), with `latest` only from attempts of the run's current revision (`results.counted`, the single place of this filter for the scoreboard, `kept` and the export), so a participant with only an older revision has none (no claim to a threshold and no place in a drawing; participation yes, because that is held by every submitted graded attempt of the run, an addendum to ADR-0053; "no more after success" lets them in again after a revision switch). Within one revision it is the order of points and without a query for the maxima. A member of a shared scoreboard counts by its own mode. Switching a revision recomputes claims only under `latest` (only that mode filters by revision). Whoever changes the revision mode or the run's current revision elsewhere than `set_display` and `_move_round` must call `rewards.refresh_run` in the same transaction (from `results` only by an import inside the function, because `rewards` imports `results`).
- The cancelling of a claim by an admin is recognised by `refresh` through `changed_by`; an automatic cancellation must therefore leave `changed_by` empty.
- Branding is owned by the domain (table `branding_configuration`, `branding.py`), palettes and the derivation of colours by the theme; the domain imports only `app.contracts`. The palette and both colours are taken as a whole from the level that selected `custom` and are stored together with `color_palette` (`set_colours`, `require_colours`). Duplicating a quiz does not copy branding (the quiz type and all its settings overrides yes), archiving leaves it. Only field names go to the audit.
- `Quiz.created_by` is set by every place that creates a quiz: a new quiz in the administration, `duplicate_quiz` (the one who copied) and the import. A new place that creates a quiz must fill it in, otherwise the quiz has no fallback contact. Older quizzes were filled in by migration `0018_quiz_created_by` (the oldest admin audit, otherwise the oldest admin).
- The contact e-mail is public. A participant's e-mail must never end up in it, only an address from branding or from an admin account.
- The scoreboard must not show an e-mail or an id; the "you" row is recognised only by the cookie (`BoardRow.key`), never by the name. `BoardRow.attempt_id` is only for the export, no template draws it.
- The export never reads the answer key, tokens or the access-code hash and omits unsubmitted attempts, test runs and attempts from test links. A new column with a number must be in `numeric`, otherwise it gets formula protection; a column with personal data belongs in a file in `PERSONAL`.
